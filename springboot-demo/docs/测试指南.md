## 一、先建立正确的心智模型

### 1.1 测试的本质

一行话说清楚：

> **给定输入 → 执行 → 断言输出符合预期。**

没有比这更复杂的。所谓"写测试"，就是把你脑子里那句"这个功能应该是这样工作的"用代码写下来，让机器每次都能替你验证一遍。

### 1.2 必须覆盖的三类路径

新手写测试最常见的毛病是**只测正常路径**。请强制自己每写一个方法，都想这三类：

| 类型 | 说明 | 例子（本项目 `TodoService.add`） |
|---|---|---|
| **正常路径** | 输入合法，结果正确 | `add("写测试")` → 成功创建，id=1 |
| **边界值** | 刚好在临界点上 | `add("")`、`add(" ")`、`add("\u3000")`、超长标题 |
| **异常路径** | 应该报错的情况 | `add(null)` → 抛 `IllegalArgumentException` |

**经验法则**：写完正常用例后，逼自己再想三个"奇怪但合法"的输入。真正出 bug 的地方几乎都在这。

### 1.3 测试金字塔

高层测试更"真实"但更慢更脆；低层测试更快更稳。**能放在低层测的，就不要放到高层。**

```
        /\        集成测试（真实 HTTP）
       /  \       ← 少而精，验证"链路通不通"
      /----\
     /      \    Web 层测试（MockMvc）
    /        \   ← 中量，验证"接口契约"
   /----------\
  /            \ 单元测试（纯 new）
 /              \← 大量，验证"业务逻辑"
/________________\
```

### 1.4 什么**不该**测

这不是偷懒，是避免维护一堆没价值的代码：

- **第三方库本身**：别去测 `String.trim()` 对不对，那是 JDK 的事
- **纯 getter/setter**：没有逻辑就没有 bug（但见 [7.3](#73-未覆盖的分支不一定是漏测)）
- **实现细节**：测"调用了哪个私有方法"会让重构寸步难行；要测**行为**

## 三、从零写一个测试用例：完整思考过程

这是全文最重要的一节。我用真实例子走一遍完整流程。

### 场景

假设现在要为新写的 `TodoService.add(String title)` 写测试。

```java
public synchronized Todo add(String title) {
    if (isBlank(title)) {
        throw new IllegalArgumentException("待办内容不能为空");
    }
    long id = sequence.incrementAndGet();
    Todo todo = new Todo(id, strip(title), false);
    store.put(id, todo);
    return todo;
}
```

### 第 1 步：读代码，找出所有分支

不要急着写。先逐行问自己"这里有没有可能走不同的路"：

| 代码位置 | 分支 |
|---|---|
| `isBlank(title)` | ① 是空白 → 抛异常 ② 不是空白 → 继续 |
| `sequence.incrementAndGet()` | 第 1 次调用得 1，第 2 次得 2…… |
| `strip(title)` | ① 首尾有空白 → 去掉 ② 没有 → 原样 |
| `store.put(...)` | 无条件执行 |

**四个分支，就是四个测试用例的起点。**

### 第 2 步：列用例清单（别急着写代码）

先在纸上（或注释里）列出来，再动手：

```
正常路径：
  ✓ 传普通标题 -> 成功创建，id=1，done=false，count 变 1
  ✓ 连续 add 三次 -> id 依次是 1、2、3

边界值：
  ✓ 标题首尾有半角空格 -> 应被去掉
  ✓ 标题首尾有全角空格 -> 应被去掉      ← 后来发现这里是 bug！
  ✓ 超长标题（10000 字符）-> 完整保存
  ✓ 中文/emoji/引号/换行 -> 原样保存

异常路径：
  ✓ null -> 抛 IllegalArgumentException
  ✓ 空串 "" -> 抛异常
  ✓ 纯空格 "   " -> 抛异常
  ✓ 纯制表符 "\t" -> 抛异常
  ✓ 纯全角空格 "\u3000" -> 抛异常       ← 后来发现这里是 bug！
```

**注意**：清单是在**写代码之前**列的。这一步的价值在于——
如果一边想一边写，你会不自觉地只写"能通过"的用例。

### 第 3 步：决定用哪一层测

问自己三个问题：

1. **需要验证 HTTP 状态码/JSON 吗？** 不需要 → 不用 MockMvc
2. **需要真实的数据库/网络吗？** 不需要 → 不用 `@SpringBootTest`
3. **不启动 Spring 能 new 出来吗？** 能 → 就用纯单元测试

`TodoService` 无外部依赖，能直接 `new`：

```java
private TodoService todoService;

@BeforeEach
void setUp() {
    todoService = new TodoService();   // 就这么简单
}
```

**结论：用最底层的单元测试。** 快、稳、定位问题精准。

### 第 4 步：写 given / when / then

每个测试方法都按这个结构写，可读性立刻不一样：

```java
@Test
@DisplayName("新增后应能查到，且初始为未完成")
void add_shouldCreateTodo() {
    // given（准备）—— 这里没有需要准备的，跳过

    // when（执行）
    Todo created = todoService.add("写第一个测试");

    // then（断言）
    assertNotNull(created);
    assertEquals(1L, created.getId());
    assertEquals("写第一个测试", created.getTitle());
    assertFalse(created.isDone(), "新建的待办应该是未完成状态");
    assertEquals(1, todoService.count());
}
```

**好处**：一眼能看出"测的是什么操作、验证了什么结果"。测试代码的读者比作者多得多，这笔投资值得。

### 第 5 步：跑起来，然后**判断失败的原因**

这一步最容易被忽视。

跑 `mvn test`，如果红了，**不要立刻改代码**。先问：

> 是我期望写错了，还是代码真的有 bug？

这个项目两种都真实发生过：

| 现象 | 真实原因 | 处理 |
|---|---|---|
| `toggle_shouldFlipBackAndForth` 失败 | **测试写错了**：`toggle()` 返回"切换后"的状态，我按"切换前"断言 | 改测试 |
| `add_fullWidthSpace_shouldThrow` 失败 | **代码有 bug**：`trim()` 去不掉全角空格 | 改代码（见[第八节](#八案例复盘测试抓出的真实缺陷)）|

**判断方法**：回到需求问一句——"用户期望的行为到底是什么？"
- 期望和代码不一致，且代码更合理 → 改测试
- 期望和代码不一致，且期望更合理 → 改代码

## 四、四层测试详解

### 4.1 第一层：纯单元测试

**文件**：`CalculatorServiceTest.java`（29 个用例）

**特征**：完全不启动 Spring，直接 `new`。

```java
@DisplayName("CalculatorService（纯单元测试，不启动 Spring）")
class CalculatorServiceTest {

    private CalculatorService calculator;

    @BeforeEach                    // ← 每个 @Test 前都执行一次
    void setUp() {
        calculator = new CalculatorService();
    }

    @Test
    @DisplayName("加法：1 + 2 = 3")  // ← 报告里显示这个中文名，不是方法名
    void add_shouldReturnSum() {
        assertEquals(3, calculator.add(1, 2));
    }
}
```

**关键注解**：

| 注解 | 作用 |
|---|---|
| `@Test` | 标记一个测试方法 |
| `@BeforeEach` | 每个测试方法前执行，用来重置状态 |
| `@DisplayName` | 给测试起可读的名字，报告里显示它 |
| `@Nested` | 嵌套分组，报告里显示成层级结构 |

**判断标准**：如果一个类不依赖 Spring 也能 `new` 出来，就该这样测。

#### 异常断言

```java
@Test
void divide_byZero_shouldThrow() {
    IllegalArgumentException ex = assertThrows(
            IllegalArgumentException.class,
            () -> calculator.divide(1, 0)     // 要执行的代码写成 lambda
    );
    assertEquals("除数不能为 0", ex.getMessage());   // 继续断言异常消息
}
```

`assertThrows` **返回捕获到的异常对象**，所以能进一步检查消息内容。只断言"抛了异常"是不够的——要确认**抛的是对的那种异常、带对的消息**。

#### 参数化测试

与其为每个数字写一个 `@Test`，不如写一个：

```java
@ParameterizedTest(name = "isEven({0}) 应为 true")
@ValueSource(ints = {0, 2, 4, 100, -2, -100})
void isEven_shouldBeTrueForEvenNumbers(int number) {
    assertTrue(calculator.isEven(number));
}

@ParameterizedTest(name = "{0} + {1} = {2}")
@CsvSource({
        "1, 2, 3",
        "0, 0, 0",
        "-1, 1, 0",
        "100, 200, 300"
})
void add_parameterized(int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}
```

报告里会显示成**独立的多个用例**，某个参数挂了能一眼看出是哪个。

#### 分组断言

```java
@Test
void assertAll_demo() {
    assertAll("计算器基础运算",
            () -> assertEquals(5, calculator.add(2, 3)),
            () -> assertEquals(1, calculator.subtract(3, 2)),
            () -> assertEquals(6, calculator.multiply(2, 3)),
            () -> assertEquals(2, calculator.divide(4, 2))
    );
}
```

**普通写法**：第一个断言失败就中断，后面的不执行，你得反复跑很多次才能修完。
**`assertAll`**：全部执行完，一次性列出所有失败项。

### 4.2 第二层：业务逻辑测试（状态隔离）

**文件**：`TodoServiceTest.java`（16 个用例）

和第一层唯一的区别：**被测对象有内部状态**，所以必须保证测试之间互不干扰。

```java
@BeforeEach
void setUp() {
    todoService = new TodoService();
    todoService.clear();   // 双保险：确保每次都是全新的服务
}
```

#### 为什么这很重要

`TodoService` 内部有个 `Map` 存数据。如果不清理：

```
测试 A：add("X")           → count = 1
测试 B：assert count == 1  → 实际是 2，失败！
```

于是出现最让人头疼的现象：**单独跑通过，一起跑就失败**。

#### 这类测试特别值得写的两条

**① 封装性**：外部拿到集合后乱改，不该影响内部数据

```java
@Test
@DisplayName("findAll 返回的是副本，修改它不影响内部数据")
void findAll_shouldReturnCopy() {
    todoService.add("A");

    List<Todo> first = todoService.findAll();
    first.clear();                                  // 恶意清空返回的列表

    assertEquals(1, todoService.findAll().size(), "内部数据不应被外部修改影响");
}
```

**② 综合场景**：多个操作串起来是否正确

```java
@Test
@DisplayName("综合：新增 3 条 -> 完成 1 条 -> 删 1 条 -> 剩余状态正确")
void scenario_fullLifecycle() {
    Todo a = todoService.add("任务A");
    Todo b = todoService.add("任务B");
    Todo c = todoService.add("任务C");

    todoService.toggle(b.getId());
    todoService.delete(c.getId());

    assertEquals(2, todoService.count());
    assertEquals(1, todoService.findUnfinished().size());
    assertTrue(todoService.findById(b.getId()).get().isDone());
    assertEquals(a.getId(), todoService.findAll().get(0).getId());
}
```

单个方法都对，组合起来不一定对。这类测试最接近"用户真实是怎么用的"。

### 4.3 第三层：Web 层测试（MockMvc）

**文件**：`TodoControllerTest.java`（11 个用例）、`HelloControllerTest.java`（4 个用例）

**核心转变**：这一层关心的不再是 Java 方法返回值，而是**状态码**和**响应 JSON**。

```java
@WebMvcTest(TodoController.class)     // ← 只启动 Web 层，不启动整个容器
@DisplayName("TodoController（MockMvc + Mockito）")
class TodoControllerTest {

    @Autowired
    private MockMvc mockMvc;          // ← 模拟 HTTP 客户端，不占真实端口

    @MockBean
    private TodoService todoService;  // ← 把 Service 换成假对象

    @Test
    void list_shouldReturnJsonArray() throws Exception {
        // given：约定假 Service 返回什么
        given(todoService.findAll()).willReturn(Arrays.asList(
                new Todo(1L, "写测试", false),
                new Todo(2L, "跑测试", true)
        ));

        // when + then：发请求并断言响应
        mockMvc.perform(get("/api/todos"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$", hasSize(2)))
                .andExpect(jsonPath("$[0].title").value("写测试"))
                .andExpect(jsonPath("$[1].done").value(true));
    }
}
```

#### 两个注解的分工

**`@WebMvcTest(XxxController.class)`**
- 只加载：Controller + 参数解析 + JSON 转换 + `@ControllerAdvice`
- **不加载**：`@Service`、`@Repository`、数据源
- 所以比 `@SpringBootTest` 快得多

**`@MockBean`**
- 用 Mockito 造一个假替身放进容器
- 默认所有方法返回 `null` / `false` / `0`
- 需要什么行为，就用 `given(...)` 提前约定

**为什么要造假对象？** 因为这一层只想验证"Controller 处理 HTTP 的逻辑"。Service 换成假的之后：
- 测试更纯粹，不受真实业务逻辑干扰
- 更容易造异常场景（想让 `add()` 抛异常？`given(...).willThrow(...)` 一行搞定）
- 更快

#### jsonPath 断言速查

| 写法 | 含义 |
|---|---|
| `jsonPath("$").exists()` | 根节点存在 |
| `jsonPath("$.title").value("x")` | 字段等于 x |
| `jsonPath("$", hasSize(2))` | 数组长度 |
| `jsonPath("$[0].id").value(1)` | 第一个元素的 id |
| `jsonPath("$.list[*].name")` | 所有 name 组成的列表 |
| `jsonPath("$.name").doesNotExist()` | 字段不存在 |

#### 测试错误路径同样重要

```java
@Test
void create_blankTitle_shouldReturn400() throws Exception {
    given(todoService.add("")).willThrow(new IllegalArgumentException("待办内容不能为空"));

    mockMvc.perform(post("/api/todos")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("{\"title\":\"\"}"))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.error").value("BAD_REQUEST"))
            .andExpect(jsonPath("$.message").value("待办内容不能为空"));
}
```

这条测试同时验证了三件事：状态码是 400、全局异常处理器生效了、错误 JSON 的格式对。

#### 顺带：安全测试

`HelloControllerTest` 里有一类特殊的测试——**安全行为必须用测试锁死**：

```java
@Test
@DisplayName("安全：name 里的 <script> 必须被转义，不能原样输出")
void hello_escapesScriptTag() throws Exception {
    mockMvc.perform(get("/hello").param("name", "<script>alert(1)</script>"))
            .andExpect(status().isOk())
            .andExpect(content().string(not(containsString("<script>"))))
            .andExpect(content().string(containsString("&lt;script&gt;")));
}
```

为什么值得单独写？因为**这类行为很容易被"优化"改坏**。
某天有人为了"让代码简洁一点"把转义逻辑删了，测试会立刻变红并阻止他合并。

### 4.4 第四层：集成测试（真实 HTTP）

**文件**：`TodoApiIntegrationTest.java`（7 个用例）

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class TodoApiIntegrationTest {

    @Autowired
    private TestRestTemplate restTemplate;   // ← 自动指向随机端口

    @Autowired
    private TodoService todoService;         // ← 真实的 Service

    @LocalServerPort
    private int port;

    @BeforeEach
    void setUp() {
        todoService.clear();   // 真身是单例，必须清理
    }
}
```

#### 和 @WebMvcTest 的本质区别

| | `@WebMvcTest` | `@SpringBootTest(RANDOM_PORT)` |
|---|---|---|
| HTTP 环境 | 假的（MockMvc） | **真的启动 Tomcat** |
| Service | `@MockBean` 假对象 | **真身** |
| 验证目标 | Controller 逻辑 | **整条链路** |
| 启动耗时 | ~0.15 s | ~2.5 s |

#### 它能发现单元测试发现不了的问题

- Bean 装配对不对、有没有循环依赖
- **JSON 序列化/反序列化**有没有问题（比如日期格式、字段名）
- 全局异常处理器生不生效
- **静态资源**能不能被访问到
- 过滤器、拦截器、字符编码设置对不对

本项目的 `indexPage_isServed` 就是一个只有集成测试才能做的验证：

```java
@Test
void indexPage_isServed() {
    ResponseEntity<String> response = restTemplate.getForEntity("/", String.class);
    assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
    assertThat(response.getBody()).contains("Spring Boot 示例首页");
}
```

#### RANDOM_PORT 的好处

用 `@LocalServerPort` 拿到随机端口，而不是写死 8080：
- 避免和本机正在运行的服务冲突（本项目的 8080 就曾被浏览器占用过）
- 多个测试类可以并行

#### TestRestTemplate 的一个便利特性

它**不会因为 4xx/5xx 抛异常**，而是正常返回带错误码的响应。所以测错误路径很自然：

## 五、断言速查表

### 5.1 JUnit 5 原生断言

```java
// 相等
assertEquals(expected, actual);
assertEquals(expected, actual, "失败时的提示信息");
assertNotEquals(unexpected, actual);

// 真假

assertFalse(condition);

```

### 5.2 AssertJ（更推荐）

比原生断言更接近自然语言，失败信息也更详细：

```java

assertThat(actual).isNotEqualTo(other);
assertThat(str).isEqualTo("x");
assertThat(str).startsWith("x").endsWith("y").contains("z");
assertThat(num).isPositive().isGreaterThan(0).isLessThan(10);

// 集合
assertThat(list).hasSize(3);
assertThat(list).isEmpty();
assertThat(list).isNotEmpty();
assertThat(list).contains("A", "B");
assertThat(list).containsExactly("A", "B", "C");   // 顺序也要对
assertThat(list).containsExactlyInAnyOrder("C", "A", "B");
assertThat(list).extracting(Todo::getTitle).containsExactly("A", "B");
assertThat(list).extracting(Todo::getId, Todo::getTitle, Todo::isDone)
        .containsExactly(tuple(1L, "A", false), tuple(2L, "B", true));

// 异常
assertThatThrownBy(() -> service.add(""))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("待办内容不能为空");

// 递归比较（对象没重写 equals 时特别有用）
assertThat(a).usingRecursiveComparison().isEqualTo(b);

// 软断言（收集所有失败，最后统一报告）
SoftAssertions softly = new SoftAssertions();
softly.assertThat(x).isEqualTo(1);
softly.assertThat(y).isEqualTo(2);
softly.assertAll();     // ← 别忘了这一句！
```

## 六、Mockito 速查

### 6.1 打桩：约定假对象的行为

```java
// 推荐：BDDMockito 风格（given/willReturn），读起来像自然语言
given(todoService.findAll()).willReturn(list);
given(todoService.findById(1L)).willReturn(Optional.of(todo));
given(todoService.delete(1L)).willReturn(true);
given(todoService.add("")).willThrow(new IllegalArgumentException("..."));
given(todoService.findById(1L)).willThrow(new RuntimeException("..."));
```

### 6.2 验证：某方法到底被调没被调

```java
then(todoService).should().findAll();                          // 调过一次
then(todoService).should(never()).delete(anyLong());           // 从没调过
then(todoService).should(times(2)).add(anyString());           // 调了恰好两次
then(todoService).should(atLeastOnce()).findAll();
```

### 6.3 参数匹配器

```java
any()            // 任意对象（含 null）
anyString()      // 任意字符串
anyLong()        // 任意 long
eq("精确值")      // 精确匹配
argThat(s -> s.startsWith("A"))   // 自定义条件
```

**注意**：一旦某个参数用了匹配器，**所有参数都得用**：

```java

// ✓ 正确

```

### 6.4 什么时候该用 Mock

**该用**：依赖是外部系统（数据库、HTTP 接口、消息队列、文件系统）——这些慢、不稳定、难造场景。
**不该用**：依赖是纯粹的计算逻辑——直接 new 真的就行，mock 了反而测不到真东西。

本项目里 `TodoService` 被 mock，是因为 `@WebMvcTest` 根本不加载它。这是"架构要求"，不是"为了 mock 而 mock"。

### 7.3 未覆盖的代码不一定是"漏测"

`Todo.java` 的 `toString()` 没被覆盖。要不要为它写测试？

**我的建议是不必。** 理由：
- 它没有逻辑分支，出错概率极低
- 为 getter/setter/toString 写测试，是典型的"为了覆盖率数字而写测试"

```java

```

**判断标准是"这段代码出错会不会有人受影响"，不是"覆盖率数字好不好看"。**

> ⚠️ **100% 覆盖率不是目标。** 覆盖率是"发现盲区"的工具，不是"绩效考核"的指标。
> 盲目追求 100% 只会让你写出一堆没有价值的测试，反而增加维护成本。

### 7.4 覆盖率还能帮你发现"代码写多了"

`TodoController` 里这一行：

**这比"多测几个 getter"有价值得多。**

## 八、案例复盘：测试抓出的真实缺陷

这是本项目最值得看的一段，完整记录一次"测试发现 bug → 修复 → 验证"的闭环。

### 8.1 起因

写 `TodoServiceEdgeCaseTest` 时，我按"边界值"的思路列了几种空白输入：

```java
@Test
@DisplayName("全角空格（\\u3000）也应被视为空白 —— 中文输入法很容易打出来")
void add_fullWidthSpace_shouldThrow() {
    assertThatThrownBy(() -> todoService.add("\u3000"))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessage("待办内容不能为空");
}
```

### 8.2 测试红了

```
Tests run: 77, Failures: 1, Errors: 0, Skipped: 0
[ERROR] TodoServiceEdgeCaseTest.add_fullWidthSpace_shouldThrow <<< FAILURE!
```

### 8.3 判断：是代码错还是期望错？

回到需求问一句：**"只有一个全角空格的待办，应该被接受吗？"**

答案显然是否定的——用户看到的是一条"空白的待办"。

所以**是代码有 bug**。

### 8.4 根因

原来的实现：

```java
if (title == null || title.trim().isEmpty()) {
    throw new IllegalArgumentException("待办内容不能为空");
}
```

问题出在 `String.trim()` 上。翻 JDK 文档：

> `trim()` 返回字符串的副本，忽略**前导空白和尾部空白**，其中空白被定义为**码点小于等于 `'\u0020'`（空格字符）**的字符。

`\u3000`（全角空格，IDEOGRAPHIC SPACE）是 **U+3000**，远大于 U+0020，所以 `trim()` 不会去掉它。

而全角空格在中文输入法下极其常见——用户按一下空格键，如果输入法没切回半角，打出来的就是 `\u3000`。

**结果**：用户能创建出一条看起来完全空白的待办。

### 8.5 修复

```java
public synchronized Todo add(String title) {
    if (isBlank(title)) {              // ← 改用自定义的 isBlank
        throw new IllegalArgumentException("待办内容不能为空");
    }
    long id = sequence.incrementAndGet();
    Todo todo = new Todo(id, strip(title), false);   // ← 改用自定义的 strip
    store.put(id, todo);
    return todo;
}

/** 判断是否全为空白（含全角空格） */
private static boolean isBlank(String text) {
    if (text == null) {
        return true;
    }
    for (int i = 0; i < text.length(); i++) {
        if (!isBlankChar(text.charAt(i))) {
            return false;
        }
    }
    return true;
}

/** 去掉首尾空白（含全角空格）。Java 8 没有 String.strip() */
private static String strip(String text) {
    int start = 0;
    int end = text.length();
    while (start < end && isBlankChar(text.charAt(start))) {
        start++;
    }
    while (end > start && isBlankChar(text.charAt(end - 1))) {
        end--;
    }
    return text.substring(start, end);
}

/** 半角空白 + 全角空格等 Unicode 空格 */
private static boolean isBlankChar(char c) {
    return Character.isWhitespace(c) || Character.isSpaceChar(c);
}
```

**为什么用两个方法判断？**

| 方法 | 作用 |
|---|---|
| `Character.isWhitespace(c)` | 覆盖空格、制表符、换行等；**不包含不间断空格**（如 `\u00A0`）|
| `Character.isSpaceChar(c)` | 覆盖 Unicode 的 SPACE_SEPARATOR 类别，**包含全角空格 `\u3000`** |

两者是互补关系，合起来才完整。

> 💡 **Java 11 起有现成的 `String.isBlank()` 和 `String.strip()`**，直接就有正确行为。
> 本项目因为环境只有 JDK 8 才需要手写。这也是升级 JDK 的一个实际收益。

### 8.6 验证

先跑测试：

```
Tests run: 77, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

再用真实 HTTP 确认（单元测试通过不代表线上行为正确）：

```powershell

# 修复后：
POST /api/todos  {"title":"\u3000"}
  → HTTP 400 {"error":"BAD_REQUEST","message":"待办内容不能为空"}   ✓

POST /api/todos  {"title":"\u3000\u3000测试全角\u3000\u3000"}
  → HTTP 201 {"id":1,"title":"测试全角","done":false}              ✓ 首尾全角空格被正确去除

POST /api/todos  {"title":"   半角空格测试   "}
  → HTTP 201 {"id":2,"title":"半角空格测试","done":false}          ✓ 回归通过
```

### 8.7 这个案例说明了什么

1. **边界值测试的价值**：`"   "` 这种用例看起来"没必要"，但它指向的是一类输入（各种空白字符），而不是一个值
2. **中文场景容易被忽略**：全角空格、全角标点——ASCII 思维下的代码在中文环境里常有盲区
3. **测试把"模糊地带"变成"明确断言"**：需求文档不会写"全角空格算不算空"，测试帮你把这个决定固化下来
4. **单元测试通过 ≠ 一切正常**：还要用集成测试/真实请求确认端到端行为

## 九、九个常见陷阱

### 1. 测试互相污染

```java
// ✗ 错误：前一个测试的数据会影响后一个
private TodoService service = new TodoService();

// ✓ 正确：每个测试前重建
@BeforeEach
void setUp() { service = new TodoService(); }
```

**症状**：单独跑通过，一起跑失败。

### 2. 期望写错了，却去改代码

测试红了先别改代码。回到需求问一句"用户期望的行为是什么"。

本项目 `toggle_shouldFlipBackAndForth` 就是**测试写错**的典型——方法返回"切换后"的状态，我按"切换前"断言了。

### 3. 断言太弱

```java
// ✗ 只断言不为 null，等于什么都没测
assertNotNull(result);

// ✓ 断言具体内容
assertEquals("写测试", result.getTitle());
assertFalse(result.isDone());
assertTrue(service.count() == 1);
```

### 4. 测实现细节，而不是行为

```java
// ✗ 依赖"内部调用了哪个私有方法"，重构就挂
assertEquals(2, service.getInternalCallCount());

// ✓ 只关心对外可观察的结果
assertEquals(2, service.findAll().size());
```

**判断标准**：如果我把内部实现完全重写（但对外行为不变），这条测试该不该挂？该挂就说明测错了地方。

### 5. 一个测试断言太多

```java
// ✗ 失败时不知道是哪一步出的问题
@Test
void everything() {
    // 创建、查询、修改、删除、断言状态…… 50 行
}

// ✓ 一个测试只验证一件事，方法名说清楚验证什么
@Test void add_shouldCreateTodoWithId1() { ... }
@Test void add_shouldTrimTitle() { ... }
@Test void add_blankTitle_shouldThrow() { ... }
```

### 6. 测试之间有执行顺序依赖

JUnit 默认**不保证**测试方法执行顺序。如果你的测试必须"先跑 A 再跑 B"，那它一定有问题。

### 7. 忘记测异常路径

```java
// 只测了这个
add_validTitle_returnsTodo();

// 忘了这些
add_null_throws();
add_empty_throws();
add_blank_throws();
```

**经验**：`if` 有几个分支，就至少要有几个测试。

### 8. mock 过头

```java
// ✗ 把纯计算逻辑也 mock 了，测了个寂寞
@Mock private CalculatorService calculator;
given(calculator.add(1, 2)).willReturn(3);
assertEquals(3, calculator.add(1, 2));   // 在测 mock 自己
```

**该 mock 的是外部依赖**（数据库、HTTP、文件系统），不是业务逻辑。

### 9. 测试代码不讲究

测试代码和产品代码一样要维护。同样需要：
- 清晰的命名（`方法名_条件_期望结果`）
- 消除重复（`@BeforeEach`、辅助方法）
- 适当注释（说明"为什么测这个"，而不是"这行在做什么"）

**测试代码的读者比作者多得多。**
